# 系统设计说明（实验室智能门户）

> **这份文档回答一个问题：一个系统的"重点"在哪。**
> 不是页面，是下面这四件事。任何网站、任何后端服务，先问这四个问题，就不会迷路。
>
> 更新：2026-10-08

---

## 一、这个系统在解决什么问题

实验室需要一个对外介绍的网站。普通网站的问题是：访客的问题（研究方向、招生要求、设备情况）在页面上找不到，只能发邮件问，而这些问题**高度重复**。

所以这个系统 = **实验室门户** + **能回答访客问题的智能助理**。

使用者有两类，这是设计的第一约束：

| 角色 | 想做什么 | 约束 |
|---|---|---|
| 访客 | 了解实验室、提问 | 不能改任何数据；提问可能被滥用 |
| 管理员（实验室成员） | 更新成员、成果、介绍、知识库文档 | 不写代码，只通过后台操作 |

## 二、数据模型：系统里有哪些"东西"

**这是第一个要问的问题。** 页面只是数据模型的投影，模型错了，页面怎么改都是错的。

| 表 | 存什么 | 谁改 | 特点 |
|---|---|---|---|
| `lab_member` | 团队成员：姓名、身份、照片、简介、排序 | 管理员 | 低频变更、有图片 |
| `lab_content` | 站点文本：首页介绍、研究方向描述 | 管理员 | 键值结构，加减字段不改表 |
| `lab_publication` | 论文成果：标题、作者、年份、链接 | 管理员 | 结构化列表 |
| `kb_document` | 知识库文档的元信息（已有） | 管理员 | 有状态机 |
| `kb_chunk` | 文档切分后的片段原文（已有） | 系统 | 与向量库同 id 绑定 |
| `qa_log` | 访客问答记录：问题、命中片段、耗时、是否答不上来 | 系统自动写 | **用来发现文档缺口** |

### 为什么 `lab_content` 用键值表，而不是给每个字段建列

站点文本会变——今天要加"实验室地址"，明天要加"开放时间"。如果每个字段一列，每次都要改表结构、改代码、重新部署。

键值表把"字段"变成"数据"，加内容不需要改代码：

```sql
CREATE TABLE lab_content (
    key        TEXT PRIMARY KEY,   -- 例如 home.intro、research.direction.1
    value      TEXT,
    updated_at TIMESTAMPTZ
);
```

**代价**：弱类型、不能约束格式、查询不直观。所以它只适合"短文本 + 字段不稳定"的场景。像 `lab_member` 这种结构固定的，就该老老实实建列。

> **面试点**：什么时候用键值表？答案就是这个权衡——字段频繁变化用键值，结构稳定用列。

### 为什么 `qa_log` 值得做

这是这个项目里最容易被忽略、但产品价值最高的一张表。

它记录：访客问了什么、检索到几段、模型答了还是说"无法确定"、耗时多少。

有了它，你就能回答这些问题：

- **访客最关心什么？** 决定首页放什么内容
- **哪些问题系统答不上来？** 说明知识库缺文档 → 补文档
- **哪些问题被反复问？** 可以做成常见问题快捷入口

**这是"数据驱动迭代"的最小闭环**：上线 → 收集真实问题 → 补文档 → 再上线。面试时你讲这个，比讲任何技术细节都有说服力，因为它证明你在运营一个产品，而不只是写代码。

## 三、状态流转：东西怎么"变"

**这是第二个要问的问题。** 一个实体有哪几个状态、怎么流转、失败了怎么办——想清楚这个，系统就不会乱。

### 文档的状态机

```
上传
  ↓
PENDING（已接收，排队中）      ← 异步化的关键：接口立刻返回，不再阻塞
  ↓  worker 取走
PROCESSING（解析 → 切分 → 向量化）
  ↓                    ↘
READY（可用）          FAILED（记录失败原因，可重试）
  ↓
已删除（向量 + 原文 + 元数据一起清理）
```

三个设计要点：

**一、为什么要有 `PENDING`。** 现在的实现是同步的——上传请求会一直阻塞到入库完成（大文档 6 秒），用户只能盯着转圈。改成异步后，接口立刻返回 `PENDING`，前端轮询进度。

**二、为什么 `FAILED` 要记录原因。** 失败是常态（格式不支持、扫描件、接口限流），没有原因就没法排查。我们之前那个 `dimensions` 参数的坑，就是靠这个机制才定位到的。

**三、为什么删除要三样一起清理。** 向量在向量库、原文在 `kb_chunk`、元信息在 `kb_document`——只删一半会留下"搜得到但看不到出处"的幽灵片段。

### 内容的状态

成员和站点内容没有复杂状态，只有"有 / 无"。但有个隐含约束：**成员删除时，他的照片文件也要清理**，否则服务器上会堆积孤儿图片。这是很多后台系统的通病。

## 四、权限矩阵：谁能改什么

**这是第三个要问的问题。** 权限想不清楚，系统就有安全漏洞。

| 资源 | 访客 | 管理员 |
|---|---|---|
| 站点内容、成员、成果 | 读 | 读 + 写 |
| 知识库文档 | **完全不可见** | 读 + 写 |
| 问答接口 | 可用（**限流**） | 可用 |
| 上传图片 | 不可 | 可 |
| 问答日志 | 不可 | 读 |

两条关键约束：

**一、问答接口对访客开放，但必须限流。** 否则任何人扫到端口就能刷你的大模型额度。这是公开站点和内部工具的根本区别。

**二、知识库文档对访客完全隐藏。** 访客能看到答案和引用来源的文件名，但看不到文档列表，更不能下载原文档。**引用可追溯**和**源文档开放**是两回事。

实现上就是给接口分两级：读接口公开，写接口要管理员口令。现有的 `AccessTokenFilter` 已经实现了口令机制，扩展一下即可。

## 五、技术映射：每个技术对应哪个约束

**这是第四个要问的问题，也是面试官最爱问的。**

技术不是想用就用，而是**某个约束的回应**。这张表是整个项目的"技术逻辑地图"：

| 约束（真实现象） | 技术 | 具体做法 | 预期收益 |
|---|---|---|---|
| 热点问题重复调嵌入接口，每次约 200ms 且有费用 | **Redis 缓存** | 缓存「问题文本 → 向量」，设 TTL | 首字延迟下降，嵌入调用量大幅减少 |
| 站点公开，接口可能被刷 | **Redis 限流** | 按 IP 的滑动窗口计数 | 保护大模型额度 |
| 大文档入库阻塞请求 6 秒以上 | **线程池异步** | 上传返回 PENDING，后台处理 | 上传秒级返回，进度可见 |
| 成员、成果经常变更 | **内容表 + 管理后台** | 结构化存储 + 表单编辑 | 改内容不用重新部署 |
| 访客问题五花八门，无法预知 | **问答日志** | 记录问题与命中情况 | 发现文档缺口，指导内容运营 |
| 前端要频繁和多个接口交互 | **前后端分离（Vue）** | REST 接口 + 前端路由 | 职责清晰，便于迭代 |

### 刻意不做的技术，和理由

**这一节比上一节更能体现判断力。**

| 技术 | 为什么不做 |
|---|---|
| **消息队列（RabbitMQ / Kafka）** | MQ 的价值在跨进程传递任务、削峰、持久化。本项目是单进程应用，任务在内存里传递即可，线程池完全够用。引入 MQ 属于为了用而用 |
| **多级缓存（Caffeine + Redis）** | 单实例部署，本地缓存和 Redis 的区别体现不出来 |
| **分布式锁** | 没有多实例竞争资源的场景 |
| **多用户 / RBAC 权限体系** | 管理员就是实验室几个人，一个口令足够。为低频操作建权限体系是过度设计 |
| **富文本编辑器** | 会引入 XSS 过滤、格式兼容、图片插入等一堆问题，而站点内容以短文本为主 |
| **Elasticsearch** | 文档规模只有几百个片段，自研的 BM25 已经够用。十万级文档时再考虑 |

> **面试技巧**：主动说"我评估过 MQ，但这个场景下线程池足够"，比强行堆一个 MQ 更值钱。
> 因为前者说明你懂边界，后者只说明你会装组件。

## 六、模块划分

```
ai-kb-agent/
├── src/main/java/com/kbagent/
│   ├── config/         配置装配（模型、向量库、Redis）
│   ├── document/       文档元数据存储
│   ├── ingest/         入库流水线（解析、切分、向量化、异步调度）
│   ├── retrieval/      检索（向量、关键词、RRF 融合、重排）
│   ├── agent/          提示词组装与生成
│   ├── lab/            【新】实验室内容：成员、站点内容、成果
│   ├── eval/           评测：评测集生成、消融实验
│   └── web/            接口层（含权限过滤、限流）
├── frontend/           【新】Vue 3 + Vite
│   ├── src/views/      访客门户
│   ├── src/admin/      管理后台（路由懒加载）
│   └── src/api/        接口封装
└── deploy/             部署脚本与容器编排
```

## 七、这份文档怎么用

**做任何新功能之前，先回来更新这四节：**

1. 数据模型变了没？（新表、新字段）
2. 状态机变了没？（新状态、新的失败路径）
3. 权限变了没？（新角色、新的可写资源）
4. 引入的技术对应哪个约束？（如果找不到约束，就要质疑该不该做）

**这四问就是"一个网站的重点在哪"的完整答案。**
