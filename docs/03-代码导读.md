## 一、全景图（先记住这张图）

```
用户在页面输入问题
   ↓  GET /api/chat/stream?question=...
ChatController.stream()               ← 第 1 站：HTTP 入口
   ↓  agentService.prepare(question, topK)
KbAgentService.prepare()              ← 第 2 站：拼提示词
   ├─→ RetrievalService.retrieve()    ← 第 3 站：检索
   │      ├─→ EmbeddingModel.embed(问题)   硅基流动 bge-m3，把文字变成向量
   │      └─→ EmbeddingStore.search()      向量库，找最像的片段
   └─→ 组装 messages：系统提示词 + 【参考资料】 + 【用户问题】
   ↓  agentService.stream(context, handler)
StreamingChatModel.chat()             ← DeepSeek，开始生成
   ↓  每生成一小段 → onPartialResponse → SSE 的 delta 事件 → 页面逐字显示
```

理解了这张图，你就理解了整个项目。剩下的都是细节。

## 二、第 1 站：HTTP 入口

**文件**：`src/main/java/com/kbagent/web/ChatController.java`　**只看**：`stream()` 方法

先看方法签名：

```java
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestParam("question") String question, ...)
```

三个点要弄明白：

- `TEXT_EVENT_STREAM_VALUE` 就是 SSE，一种"服务端可以持续往浏览器推消息"的协议。普通接口是"一问一答"，SSE 是"一问持续答"。
- `SseEmitter` 是 Spring 给的服务端句柄，拿着它就能随时往浏览器发消息。
- 返回 `SseEmitter` 而**不是**返回字符串，意味着这个方法会先返回、之后慢慢往里推数据。

再看推送顺序：

```java
AgentContext context = agentService.prepare(question, topK);   // 先检索
emit(emitter, "sources", toSourceRefs(context));               // ① 立刻把引用来源推给前端
agentService.stream(context, new StreamingChatResponseHandler() {
    public void onPartialResponse(String partialResponse) {    // ② 模型每吐一小段
        emit(emitter, "delta", partialResponse);               //    就推一个 delta 事件
    }
    public void onCompleteResponse(ChatResponse response) {    // ③ 生成结束
        emit(emitter, "done", Map.of(...));                    //    推完整答案和耗时
        emitter.complete();                                    //    关闭连接
    }
    public void onError(Throwable error) { ... }               // ④ 出错也要关连接
});
```

**为什么要先推 `sources`？** 因为检索是同步的、很快（实测 200 毫秒左右），而模型生成要一到两秒。先推来源，用户能立刻看到"系统找到了哪些资料"，等待感大幅降低。这是产品体验上的设计，不是技术必需。

最后注意 `emit()` 方法自己吞掉了异常：

```java
private void emit(SseEmitter emitter, String event, Object data) {
    try {
        emitter.send(SseEmitter.event().name(event).data(data));
    } catch (Exception e) {
        log.debug("SSE 发送失败（客户端可能已断开）: {}", e.getMessage());
    }
}
```

用户切走标签页、关掉浏览器，连接就断了，写数据必然失败。这是**常态不是异常**，所以只记 debug 日志，不往上抛。

3. 客户端断开连接时，代码会发生什么？为什么不能把这种失败当成错误抛出？

## 三、第 2 站：拼提示词

**文件**：`src/main/java/com/kbagent/agent/KbAgentService.java`　**只看**：`SYSTEM_PROMPT`、`prepare()`、`buildUserPrompt()`

### 系统提示词的五条规则，每条都在解决一个具体问题

```java
1. 只使用参考资料中的信息，不得引入外部知识，不得凭常识推测。
2. 如果资料不足以回答，直接说明"根据现有资料无法确定"，并指出还缺什么信息。
3. 每个结论后面用 [1]、[2] 这样的编号标注来源，编号必须与参考资料序号一致。
4. 多条资料互相冲突时，指出冲突并分别标注来源，不要擅自选一个。
5. 用简洁的中文回答，先给结论，再给依据，不要重复资料原文。
```

| 规则 | 解决的问题 | 实测效果 |
|---|---|---|
| 1 | 幻觉：模型拿自己的知识补答案 | 配合规则 2，问"作者邮箱"时正确拒绝了 |
| 2 | 硬答：不知道也编一个 | 生效，会说明缺什么信息 |
| 3 | 无法追溯：答案从哪来 | 页面上的 [1][2] 角标 |
| 4 | 多来源冲突：只能选一个 | 多文档场景才明显 |
| 5 | 输出啰嗦：复述原文 | 答案更短，演示更清爽 |

### 参考资料是怎么拼出来的

```java
prompt.append("【参考资料】\n");
for (int i = 0; i < chunks.size(); i++) {
    prompt.append('[').append(i + 1).append("] 文件：").append(chunk.fileName());
    if (chunk.section() != null && !chunk.section().isBlank()) {
        prompt.append("｜章节：").append(chunk.section());
    }
    prompt.append('\n').append(truncate(chunk.text())).append("\n\n");
}
prompt.append("【用户问题】\n").append(question);
```

三个细节：

- **`i + 1` 就是规则 3 里说的编号**，和页面上显示的引用角标是同一个数字。这是"引用可追溯"的实现核心。
- **带上文件名和章节名**，模型回答时能说清是哪个文件的哪一节，用户也能核对。
- **`truncate` 把单个片段截到 1200 字**，因为提示词太长会变贵、也可能超出模型上下文。

注意 `prepare()` 里还有一句：

```java
if (chunks.isEmpty()) {
    prompt.append("（没有检索到任何相关资料）\n");
}
```

检索为空时不要什么都不给，否则模型会以为自己在做普通问答，直接凭知识回答。

## 四、第 3 站：检索

**文件**：`src/main/java/com/kbagent/retrieval/RetrievalService.java`　**只看**：`retrieve()`

整个方法只有十几行，但它是 RAG 的核心：

```java
int maxResults = topK != null && topK > 0 ? topK : properties.getRetrieval().getMaxResults();
Embedding queryEmbedding = embeddingModel.embed(query).content();   // 把"问题"也变成向量

EmbeddingSearchRequest request = EmbeddingSearchRequest.builder()
        .queryEmbedding(queryEmbedding)
        .maxResults(maxResults)                               // 取最像的 6 段
        .minScore(properties.getRetrieval().getMinScore())    // 相似度低于 0.35 的不要
        .build();

return embeddingStore.search(request).matches().stream()
        .map(match -> new RetrievedChunk(
                match.embeddingId(),
                match.embedded().text(),
                match.embedded().metadata().getString("file_name"),
                match.embedded().metadata().getString("section"),
                parseInt(match.embedded().metadata().getString("chunk_index")),
                match.score()))
        .toList();
```

**检索的原理，一句话讲清**：入库时把每个片段送进向量模型，得到一串 1024 个数字（向量），语义相近的文本，向量方向也相近。提问时把问题也变成向量，然后在库里找"方向最接近"的那几段。

所以它是**按语义找，不是按关键词匹配**——这既是优点，也是短板（见第 12 题）。

两个参数要理解清楚：

- `maxResults` = 6：给模型看多少段资料。小了可能漏，大了会稀释注意力还可能超出上下文。
- `minScore` = 0.35：相似度下限。调高更精准但可能一段都召回不到；调低召回多但噪声大。

返回的 `RetrievedChunk` 里带上了 `fileName` 和 `section`，这两个值来自入库时写进向量库的元数据——所以**入库和检索是通过元数据串起来的**。

9. `minScore` 调高或调低分别会带来什么问题？

## 五、第 4 站：装配

**文件**：`src/main/java/com/kbagent/config/LangChainConfig.java`

这里定义了四个 Bean：对话模型、流式对话模型、向量模型、向量库。**记住一句话：它们是四个互相独立的东西，可以任意替换供应商**——换成百炼的向量模型、换成通义千问的对话模型，只改配置，不改业务代码。这就是面向接口编程的实际价值。

重点看 `applyThinkingMode`：

```java
Map<String, Object> custom = new LinkedHashMap<>();
custom.put("thinking", Map.of("type", thinking.trim().toLowerCase()));
... .customParameters(custom);
```

DeepSeek 的思考模式开关不在标准协议里，需要用 `customParameters` 塞到请求体顶层。这就是"OpenAI 兼容"的真实含义：**大框架兼容，各家都有自己的扩展字段**。

再看 `requireKey`：没有 key 时不抛异常，只打警告并返回占位符。理由是"本地先把页面跑起来"是刚需，key 可能晚一步才拿到。这是个刻意的取舍，面试被问到可以这么答。

## 六、另一条线：文档入库

**文件**：`src/main/java/com/kbagent/ingest/DocumentIngestionService.java`　**只看**：`ingest()`、`buildSegments()`、`embedAndStore()`

入库流水线一共六步，日志里每一步都有打印，对照着看：

```
1. 解析      TextExtractor        pdf / docx / md / txt → 纯文本
2. 体检      warnIfLikelyScanned  文本太少就警告（扫描件）
3. 章节切分  ContentSectioner     先按标题切成章节
4. 长度切分  DocumentSplitters    每章再切成 800 字、重叠 120 字的小段
5. 向量化    embedAndStore        分批（16 个一批）送向量模型，失败重试
6. 落库      repository           向量存向量库，原文和元数据存 kb_chunk
```

**为什么先按章节切再按长度切？** 只按固定长度切，会把标题和正文切散，检索到的片段经常"没有上下文"。带上章节名之后，召回质量更高，回答里的引用位置也更可信。

**为什么是 800 字、重叠 120 字？** 800 字大约是一段完整论述的长度，太小会丢上下文，太大会稀释语义；重叠是为了防止一句话正好被切断在两段之间。**注意：这两个数字目前是经验值，还没有实验依据**——这正是 10/12 建评测集之后可以验证的事。

**为什么要分批向量化？** 整份文档的片段一次性发过去，请求体太大容易被限流或超时。分批（默认 16）加指数退避重试，实测 111 个片段分 7 批、6.4 秒完成。

**删除文档时为什么必须两条一起删？** 向量存在向量库，原文存在 `kb_chunk`，两者用同一个 id 绑定。只删一边，就会出现"搜得到但看不到出处"的幽灵片段。
