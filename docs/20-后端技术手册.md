# 一、Redis 缓存：把重复计算挡在模型前面

## ① 场景

每次问答都要把问题送进嵌入模型算一次向量：**约 200 毫秒，而且是付费接口**。

热点问题的重复率极高——"研究方向是什么""怎么联系"这类问题，访客会反复问。每次重算，纯属浪费。

实测口径：一次问答首字延迟约 1.0 秒，其中约 200ms 花在嵌入计算上。

**关键判断：缓存什么？** 不是"什么数据重要"，而是**"什么数据会被重复读取"**。

- 问题：热点问题重复率高 → 值得缓存
- 文档片段：同一个知识库里几乎不重复 → 缓存只会白占内存、还拉低命中率

## ② 代码

核心实现（`retrieval/QueryEmbeddingCache.java`）：

```java
public Embedding embed(String query) {
    if (!Boolean.TRUE.equals(properties.getCache().getEnabled())) {
        return embeddingModel.embed(query).content();   // 关闭缓存时直连
    }
    String key = cacheKey(query);
    Optional<String> cached = redisOps.get(key);
    if (cached.isPresent()) {
        hits.incrementAndGet();
        return Embedding.from(decode(cached.get()));    // 命中：省掉一次 200ms 的接口调用
    }
    Embedding embedding = embeddingModel.embed(query).content();
    misses.incrementAndGet();
    redisOps.set(key, encode(embedding.vector()), Duration.ofHours(properties.getCache().getTtlHours()));
    return embedding;                                    // 未命中：算完立刻回填
}
```

key 的设计：

```java
private String cacheKey(String query) {
    // 用哈希不用原文：一是避免超长 key，二是避免把访客问题明文写进 Redis
    // 带上模型名：换嵌入模型时缓存自动失效，不会读到旧模型算的向量
    return "kb:emb:" + properties.getEmbedding().getModel() + ":" + sha256(query);
}
```

存储编码：

```java
private String encode(float[] vector) {
    ByteBuffer buffer = ByteBuffer.allocate(vector.length * Float.BYTES);
    for (float value : vector) buffer.putFloat(value);
    // 1024 维向量：JSON 约 20KB，base64 只要约 5.5KB，省了四分之三
    return Base64.getEncoder().encodeToString(buffer.array());
}
```

容错降级（`infra/RedisOps.java`）：

```java
public Optional<String> get(String key) {
    try {
        return Optional.ofNullable(redis.opsForValue().get(key));
    } catch (Exception e) {
        degrade("读取", e);        // 只告警一次，避免日志被刷爆
        return Optional.empty();   // 当作未命中：照常走模型，服务不中断
    }
}
```

## ③ 原理

**Redis 为什么快**：纯内存操作（没有磁盘 IO）、单线程执行命令（没有锁竞争和上下文切换）、IO 多路复用（一个线程管理大量连接）。Redis 6 之后网络 IO 是多线程，但命令执行仍是单线程——**这个单线程恰恰是它简单可靠的原因**。

**为什么这套缓存不需要考虑"更新策略"**：缓存的是"问题 → 向量"的映射，这是一个**纯函数**的结果——同一个问题在同一个模型下算出来的向量永远一样。没有"数据变更"就无所谓缓存失效，只需要 TTL 控制内存占用。

**为什么 base64 比 JSON 省**：JSON 里每个浮点数要占十多个字符，而 float32 在内存里只占 4 字节。base64 编码后约 5.5 个字符，而且浮点是二进制精确转换，**没有精度损失**。

## ④ 边界

| 情况 | 是否适合这套方案 |
|---|---|
| 缓存的是纯函数结果（同样输入永远同样输出） | 适合，无需考虑失效 |
| 缓存的是会变的数据（用户资料、库存） | 要改用 Cache-Aside，写时删缓存 |
| 数据量极大、内存放不下 | 要么换方案，要么只缓存热点（LRU） |
| 一致性要求极高（余额、库存扣减） | 缓存会带来一致性风险，应直接读库 |

## ⑤ 简历怎么写

> 为问答链路的嵌入调用引入 Redis 缓存，以「问题哈希 → 向量」为键缓存热点查询，用 base64 编码 float32 数组使单条缓存内存占用降低约 75%；配合模型名做 key 前缀，保证切换嵌入模型时缓存自动失效。

## ⑥ 面试怎么答

**Q：缓存 key 怎么设计的？为什么用哈希不用原文？**

> key 是 `kb:emb:{模型名}:{问题文本的 SHA-256}`。用哈希有两个原因：一是避免超长 key，用户可能输入几百字；二是避免把访客的问题明文写进 Redis。加模型名是为了将来换嵌入模型时缓存自动失效，不会读到旧模型算出来的向量。

**Q：缓存怎么更新？会不会脏读？**

> 这里缓存的是"问题 → 向量"的映射，是一个纯函数的结果——同一个问题在同一模型下算出来的向量永远一样。所以不存在脏数据问题，只需要 TTL 控制内存占用，我们设的 7 天。

**Q：那如果缓存的是会变的数据呢？**

> 那就要用 Cache-Aside：读时先查缓存、未命中查库回填；写时**先更新数据库、再删除缓存**（是删除不是更新，顺序也不能反）。其他还有 Write-Through、Write-Behind，但复杂度更高，一般用 Cache-Aside 就够。

**Q：缓存穿透、击穿、雪崩分别怎么处理？**

> 穿透：查一个数据库也不存在的 key，解法是缓存空值加短 TTL，或用布隆过滤器。
> 击穿：热点 key 刚过期，大量请求同时回源，解法是互斥锁只让一个请求回源。
> 雪崩：大量 key 同时过期，解法是 TTL 加随机偏移。
> 我们这里缓存的是纯函数结果，穿透风险很低，主要该防的是雪崩——给 TTL 加随机偏移是可改进的点。

**Q：Redis 挂了怎么办？**

> 降级：缓存读不到就当作未命中，照常调模型；限流执行不了就放行。这是"可用性优先"的取舍——缓存失效只是慢一点，而拒绝服务会让网站直接不可用。
> 反过来，支付扣费这类系统必须"正确性优先"，依赖挂了就该拒绝服务。取舍取决于业务对"出错"和"不可用"哪个更敏感。

**Q：为什么只缓存问题向量，不缓存检索结果？**

> 检索结果依赖知识库的当前状态——一旦上传或删除文档，缓存的检索结果就是错的。而"问题向量"只依赖模型，与知识库无关，所以是安全的。
> 判断一个数据能不能缓存，看的是**它依赖什么、什么时候会变**。

# 二、Redis 滑动窗口限流：公开站点的第一道护栏

## ① 场景

站点对公众开放。接口一旦暴露，**任何人扫到端口都能刷你的大模型额度**。

这不是"可能被攻击"，而是上线当天就会发生——**爬虫和端口扫描器是自动运行的，不需要有人针对你**。

一次问答约 5500 token 输入，单次成本虽然只有几分钱，但被脚本循环调用，一晚上就能把额度刷光。

## ② 代码

Lua 脚本（`infra/RateLimiter.java`）：

```lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local member = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)    -- 清掉窗口外的记录
local count = redis.call('ZCARD', key)                  -- 数窗口内的请求数
if count >= limit then
    return 0                                            -- 超限，拒绝
end
redis.call('ZADD', key, now, member)                    -- 记录本次请求
redis.call('EXPIRE', key, math.ceil(window / 1000) + 1) -- 兜底：防止冷 key 永久残留
return 1
```

调用侧：

```java
public boolean allow(String identifier) {
    if (!Boolean.TRUE.equals(properties.getRateLimit().getEnabled())) return true;
    long now = System.currentTimeMillis();
    // member 用「时间戳-随机数」，避免同一毫秒的两个请求互相覆盖
    String member = now + "-" + ThreadLocalRandom.current().nextInt(1_000_000);
    Long result = redisOps.execute(RATE_LIMIT_SCRIPT,
            List.of("kb:rl:" + identifier),
            String.valueOf(now),
            String.valueOf(properties.getRateLimit().getWindowSeconds() * 1000L),
            String.valueOf(properties.getRateLimit().getLimit()),
            member);
    return result == null || result == 1L;   // Redis 不可用时放行（可用性优先）
}
```

客户端 IP 的取法（`web/RateLimitFilter.java`）：

```java
private String clientIp(HttpServletRequest request) {
    if (Boolean.TRUE.equals(properties.getRateLimit().getTrustForwardedHeader())) {
        String forwarded = request.getHeader("X-Forwarded-For");
        if (forwarded != null && !forwarded.isBlank()) {
            return forwarded.split(",")[0].trim();
        }
    }
    // 默认只信 TCP 来源地址：X-Forwarded-For 客户端可以随便伪造
    return request.getRemoteAddr();
}
```

## ③ 原理

**为什么滑动窗口比固定计数器好。** 固定窗口有边界漏洞：限制"每分钟 10 次"，攻击者可以在**第 59 秒打 10 次、第 61 秒再打 10 次**——两秒内通过 20 次，但每个窗口的计数都没超。

滑动窗口记录每次请求的时间戳，任意时刻只看"过去 60 秒"，没有这个漏洞。

**为什么必须用 Lua。** "清理 → 计数 → 判断 → 写入"这四步如果分开执行，并发请求会交错：

```
请求 A 读到 count = 9（未超限）
请求 B 也读到 count = 9（也未超限）
两个都写入 → 实际变成 11 次
```

**Redis 执行 Lua 脚本是原子的**，整个脚本执行期间不会被其他命令打断。

**为什么 ZSET 适合做滑动窗口**：score 存时间戳，就能按时间范围删除；member 保证同一毫秒的多个请求不会被覆盖。

## ④ 边界

| 方案 | 适用场景 | 代价 |
|---|---|---|
| 固定窗口计数器 | 对精度要求不高的粗粒度限流 | 边界处会放过双倍流量 |
| **滑动窗口（ZSET）** | 精确限制单位时间内的总量 | 内存占用与请求数成正比 |
| 令牌桶 | 允许可控突发（API 网关按容量放行） | 参数不好调，突发量不好预估 |
| 漏桶 | 强制恒定速率（流量整形） | 不允许任何突发 |

我们的需求是"防止某个 IP 短时间刷接口"，滑动窗口最直观、最好调参。

## ⑤ 简历怎么写

> 站点公开后为问答接口设计基于 Redis ZSET 的滑动窗口限流，用 Lua 脚本保证「清理-计数-判断-写入」四步的原子性，避免并发下计数失准；默认不信任可伪造的 X-Forwarded-For 请求头，防止绕过。

## ⑥ 面试怎么答

**Q：为什么用滑动窗口不用令牌桶？**

> 令牌桶适合"允许可控突发"的场景——桶里攒了令牌就能一次性放行一批，适合 API 网关按容量放行。我们的需求是"防止某个 IP 短时间刷接口"，滑动窗口更直观、更好调参。
> 区别在于：**令牌桶约束的是平均速率加突发上限，滑动窗口约束的是任意时间窗内的总量。**

**Q：为什么要用 Lua，用 Redis 事务不行吗？**

> Redis 的 MULTI/EXEC 事务**不支持在事务中读取中间结果做判断**——它只能保证命令按顺序执行不被插入，但"读到的 count 是多少"不能用来决定后续命令。而限流恰恰需要"先读计数、再决定写不写"。Lua 脚本在 Redis 里是原子执行的，可以任意读写并做分支判断。

**Q：为什么不能信 X-Forwarded-For？**

> 这个请求头是**客户端可以随便伪造的**。不加判断就信任它，攻击者填一个假 IP 就绕过了限流。只有确实部署在可信代理（比如 Nginx）后面、由代理覆写这个头时才能信任。所以我们做成了配置项，默认关闭。

**Q：多实例部署时限流会失效吗？**

> 如果每个实例在本地内存里计数，实际限额会变成"N 个实例乘单实例限额"。所以状态必须放共享存储——这也是我们把计数器放 Redis 的原因。用 Lua 保证原子性在分布式场景下更关键。

**Q：429 还应该返回什么？**

> 标准做法还应该返回 `Retry-After` 头，告诉客户端多久后可以重试。我们目前没返回，是已知的改进点。

# 三、异步入库：线程池与状态机

## ① 场景

文档入库原本是**同步**的：上传请求要一直阻塞到解析、切分、向量化全部完成——实测 111 个片段要 **6.4 秒**。

三个问题：

1. 用户盯着转圈 6 秒以上，不知道进行到哪一步
2. 每个上传请求**占着一个 Tomcat 请求线程**，并发几个上传就把 Web 线程池占满
3. 文件越大等待越久，体验线性恶化

## ② 代码

线程池配置（`config/AsyncConfig.java`）：

```java
@Bean(name = DOCUMENT_EXECUTOR)
public ThreadPoolTaskExecutor documentExecutor(AppProperties properties) {
    AppProperties.Ingest config = properties.getIngest();
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(config.getCorePoolSize());     // 2：IO 密集型，线程不用多
    executor.setMaxPoolSize(config.getMaxPoolSize());       // 4：队列满后的扩容上限
    executor.setQueueCapacity(config.getQueueCapacity());   // 50：缓冲队列
    executor.setThreadNamePrefix("doc-ingest-");            // 便于日志排查
    // 关键：不用 CallerRunsPolicy，避免 Tomcat 线程被拖去做 6 秒的入库任务
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
    executor.initialize();
    return executor;
}
```

异步提交与同步入口（`ingest/DocumentIngestionService.java`）：

```java
/** 异步入库：界面上传用，立刻返回 PENDING */
public DocumentRecord submit(String fileName, String contentType, byte[] bytes) {
    DocumentRecord pending = createPending(fileName, contentType, bytes);
    try {
        documentExecutor.execute(() -> process(pending.id(), fileName, bytes));
    } catch (RejectedExecutionException e) {
        // 队列满：立刻落成 FAILED，让用户看到明确原因，而不是一直等
        repository.updateProgress(pending.id(), DocumentRecord.STATUS_FAILED,
                "队列已满", 0, 0, "服务器繁忙，请稍后重试");
        throw new IllegalStateException("服务器繁忙，请稍后重试");
    }
    return pending;
}

/** 同步入库：批量导入和评测用，调用方需要结果确定性 */
public DocumentRecord ingestNow(String fileName, String contentType, byte[] bytes) {
    DocumentRecord pending = createPending(fileName, contentType, bytes);
    return process(pending.id(), fileName, bytes);
}
```

处理过程与异常兜底：

```java
private DocumentRecord process(UUID documentId, String fileName, byte[] bytes) {
    try {
        update(documentId, PROCESSING, "解析文档", 5);
        String text = textExtractor.extract(fileName, bytes);
        update(documentId, PROCESSING, "切分文档", 15);
        List<TextSegment> segments = buildSegments(documentId, fileName, text);
        List<String> vectorIds = embedAndStore(documentId, segments);
        repository.updateProgress(documentId, READY, "完成", 100, chunks.size(), null);
        return repository.findById(documentId).orElseThrow();
    } catch (Exception e) {
        // 必须捕获所有异常：后台线程抛出的异常没人接，
        // 用户会永远停在"处理中"的假象里
        repository.updateProgress(documentId, FAILED, "处理失败", 0, 0, truncate(e.getMessage()));
        return repository.findById(documentId).orElseThrow();
    }
}
```

## ③ 原理

状态机的划分：

```
上传 → PENDING(排队中) → PROCESSING(解析→切分→向量化) → READY
                                        ↘ FAILED(记录原因)
```

**状态和进度是两回事**：状态是给**程序**判断的（能不能用），进度是给**用户**看的（还要等多久），不能互相替代。

**为什么线程数是 2 而不是 20**：入库是 **IO 密集型**——时间几乎都花在等嵌入接口返回，CPU 基本闲着。线程开太多，反而会因为并发请求过多被服务端限流。**线程数的判断依据是"任务在等什么"，不是"任务有多少"。**

## ④ 边界：为什么这里不该上消息队列

MQ 的价值有三个：跨进程传递任务、削峰、任务持久化。

| MQ 的价值 | 我们的情况 |
|---|---|
| 跨进程传递任务 | 不成立：单进程应用，任务在内存里传递就够 |
| 削峰 | 不成立：实验室网站，不会出现瞬时大量上传 |
| 任务持久化（重启不丢） | 勉强成立，但为此引入 RabbitMQ 不划算 |

**所以这里用线程池是经过权衡的，不是不知道 MQ。** 能说清"为什么不用"，比强行堆一个 MQ 更有说服力。

## ⑤ 简历怎么写

> 将文档入库从同步阻塞改造为异步任务：上传接口立即返回 202 与任务状态，后台线程池按「解析 → 切分 → 向量化」分阶段推进并回写进度，前端轮询展示；选择 AbortPolicy 拒绝策略，避免过载从入库线程池扩散到 Web 线程池。

## ⑥ 面试怎么答

**Q：为什么用线程池不用消息队列？**

> MQ 的价值是跨进程传递任务、削峰、任务持久化。我们是单进程应用，任务在内存里传递就够了；网站量级也没有削峰需求。唯一勉强成立的是"重启时任务不丢"，但为此引入 RabbitMQ 的部署运维成本不划算，而且用户重新上传即可。**所以这是经过权衡的选择，不是不知道 MQ。**

**Q：拒绝策略为什么用 AbortPolicy？**

> `CallerRunsPolicy` 会让**调用线程自己执行任务**——也就是 Tomcat 的请求线程去跑 6 秒的入库任务。结果是 Web 线程池也被占满，**一个组件的过载会扩散成整个服务不可用**。
> `AbortPolicy` 直接抛异常，我们捕获后把状态改成 FAILED 并返回明确错误。宁可明确拒绝一部分请求，也不要让雪崩传染。

**Q：异步之后怎么知道处理好了？**

> 状态机加前端轮询。上传返回 202 和 PENDING 记录，前端每 2 秒查一次列表，全部变成 READY/FAILED 就停。更优雅的是 SSE 推送进度，但对这种几十秒内完成的短任务，轮询更简单、更好排查。

**Q：后台任务失败了怎么办？**

> 三层：一是 `process()` 捕获所有异常（后台线程抛异常没人接，用户会永远停在"处理中"）；二是把失败原因写回数据库，前端能看到；三是向量化环节有指数退避重试 3 次。
> 没做"自动重入队列"，因为入库失败大多是数据问题（格式不支持、扫描件），自动重试没意义，应该让用户换文件。

**Q：为什么还保留一个同步入口？**

> 批量导入和评测需要"入库完成才能继续"的语义。如果都用异步，评测会在文档还没入库完时开始跑，结果全错。**同一个能力提供两个入口，是适配不同调用方的需求。**

# 四、两级权限：公开白名单 + 默认拒绝

## ① 场景

站点有两类使用者：**访客**只能浏览和提问，**管理员**才能改内容。后台接口绝不能暴露。

同时又不能把所有接口都锁上——访客要能打开页面、要能提问。

## ② 代码

`web/AccessTokenFilter.java`：

```java
@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain chain) throws ServletException, IOException {
    String uri = request.getRequestURI();
    if (!uri.startsWith("/api/")) {          // 静态页面放行，否则用户连输入口令的入口都没有
        chain.doFilter(request, response);
        return;
    }
    boolean adminOnly = !isPublic(uri, request.getMethod());
    String required = adminOnly ? adminToken : visitorToken;
    List<String> provided = resolveTokens(request);

    if (required == null || required.isBlank() || containsMatch(provided, required)) {
        chain.doFilter(request, response);
        return;
    }
    reject(response, adminOnly ? "需要管理员口令" : "访问口令不正确或缺失");
}

/** 公开路径：站点内容只读、问答接口。其余一律按管理员处理 */
private boolean isPublic(String uri, String method) {
    if (uri.startsWith("/api/chat")) return true;
    return "GET".equalsIgnoreCase(method) && uri.startsWith("/api/lab/");
}
```

恒定时间比较：

```java
private boolean containsMatch(List<String> provided, String required) {
    byte[] expected = required.getBytes(StandardCharsets.UTF_8);
    for (String candidate : provided) {
        // 用恒定时间比较：普通 equals 在第一个不同字符处返回，
        // 攻击者能通过响应时间逐字符猜出口令
        if (MessageDigest.isEqual(expected, candidate.getBytes(StandardCharsets.UTF_8))) {
            return true;
        }
    }
    return false;
}
```

## ③ 原理

**为什么用白名单 + 默认拒绝。** 以后新增接口时如果忘了配权限：白名单的最坏结果是"访问不了"（太严，用户会反馈），黑名单的最坏结果是"被人写了数据"（太松，可能很久才发现）。

**安全设计上，默认拒绝永远比默认放行安全**，这是"失效安全"（fail-safe）原则的应用。

**为什么支持 cookie**：SSE（`EventSource`）不能自定义请求头，只能靠 cookie 传递凭证。所以口令要同时支持请求头、cookie、查询参数三种来源。

## ④ 边界

| 条件 | 该用什么 |
|---|---|
| 管理员 1~5 人，只有"改内容"一个动作 | **共享口令（当前方案）** |
| 需要区分角色（编辑只能改成员） | Spring Security + RBAC |
| 需要操作审计（谁改了什么） | 完整用户体系 + 操作日志表 |
| 对外的付费用户 | OAuth2 / JWT + 刷新令牌 |

## ⑤ 简历怎么写

> 设计「公开白名单 + 默认拒绝」的两级访问控制：站点内容只读与问答接口公开，其余接口需管理员口令；口令比较使用恒定时间算法防止时序侧信道攻击，并同时支持请求头与 Cookie 以兼容 SSE 场景。

## ⑥ 面试怎么答

**Q：为什么不用 JWT 或 Session？**

> 管理员就是实验室几个人，功能只有"改内容"，一个共享口令足够。JWT 要处理签名、过期、刷新、吊销；Session 要处理存储和分布式共享。**为一个低频操作建一套完整认证体系是过度设计。**
> 如果以后要区分角色或做操作审计，就该换成 Spring Security + JWT。

**Q：明文口令放配置里安全吗？**

> 不理想。我们放环境变量并把文件权限设成 600，比硬编码好，但更严格应该存 bcrypt 哈希或用密钥管理服务。这是我知道但还没做的改进点。

**Q：为什么用恒定时间比较？**

> 普通字符串比较在遇到第一个不同字符时就返回，攻击者可以通过**测量响应时间**判断"猜对了几位"，从而逐字符暴力破解。恒定时间算法无论对错都执行相同的工作量。

**Q：静态页面为什么不需要口令？**

> 因为访客需要一个输入口令的入口。如果连页面都拦住，用户根本打不开，就陷入死循环了。

# 五、文件上传：安全与工程细节

## ① 场景

管理后台要支持上传成员照片。看起来是个小功能，但**上传是 Web 应用最常被利用的入口之一**。

三条保护，每条都对应一个真实会发生的坑。

## ② 代码

`infra/FileStorage.java`：

```java
@Component
public class FileStorage {
    private static final Set<String> ALLOWED_EXTENSIONS = Set.of("jpg", "jpeg", "png", "webp");
    private static final long MAX_BYTES = 2 * 1024 * 1024L;

    public String save(MultipartFile file) {
        if (file.getSize() > MAX_BYTES) {
            throw new IllegalArgumentException("图片超过 2MB，请压缩后再上传");
        }
        String extension = extensionOf(file.getOriginalFilename());
        if (!ALLOWED_EXTENSIONS.contains(extension)) {
            throw new IllegalArgumentException("只支持 jpg / png / webp 格式");
        }
        // 用 UUID 重命名：防覆盖、防中文和特殊字符、防 ../ 路径穿越
        String fileName = UUID.randomUUID().toString().replace("-", "") + "." + extension;
        file.transferTo(root.resolve(fileName));
        return "/uploads/" + fileName;
    }

    /** 删除时校验路径必须在上传目录内，防止越界删除 */
    public void delete(String publicPath) {
        Path target = root.resolve(publicPath.substring("/uploads/".length())).normalize();
        if (!target.startsWith(root)) {
            log.warn("[存储] 拒绝删除越界路径: {}", publicPath);
            return;
        }
        Files.deleteIfExists(target);
    }
}
```

静态资源映射（`config/WebConfig.java`）：

```java
@Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    // 上传目录在 jar 之外，所以重新部署不会丢照片
    registry.addResourceHandler("/uploads/**")
            .addResourceLocations(fileStorage.root().toUri().toString());
}
```

## ③ 原理

| 措施 | 不做的后果 |
|---|---|
| 扩展名白名单 | 有人上传 `.jsp` / `.html`，可能变成挂马点或被当作脚本执行 |
| 大小限制 | 团队照片动辄几 MB，拖慢页面、塞满磁盘 |
| UUID 重命名 | 用原文件名可能覆盖已有文件；中文、空格、`../` 会带来路径问题 |
| 路径越界校验 | 删除接口可能被利用来删除任意文件 |

**还有一条容易忘的**：删除成员时要一起删照片，否则服务器上会堆积孤儿图片。这是很多后台系统的通病——数据删了，文件还在。

**存储位置**：必须挂容器卷，否则每次重新部署照片全丢。和数据库要持久化是同一个道理。

## ④ 边界

| 规模 | 方案 |
|---|---|
| 几百张图片、单机部署 | **本地磁盘 + 容器卷（当前方案）** |
| 多实例部署 | 必须换共享存储，否则实例 A 上传的图片在实例 B 上访问不到 |
| 图片量大、需要 CDN | 对象存储（OSS/S3）+ 预签名 URL 直传，应用只存 URL |

## ⑤ 简历怎么写

> 实现图片上传的完整防护链路：扩展名白名单 + 2MB 大小限制 + UUID 重命名 + 路径越界校验，并将上传目录挂载为容器卷保证重新部署不丢文件。

## ⑥ 面试怎么答

**Q：怎么防止上传目录被当作 Web 根目录执行脚本？**

> 四层：扩展名白名单、存储目录不在 Web 可执行路径下、由应用而不是 Web 服务器提供文件访问、文件名重命名。更严格的做法是存到对象存储，文件根本不落在应用服务器上。

**Q：大文件上传怎么优化？**

> 分片上传加断点续传；前端先压缩（图片用 canvas）；或者用预签名 URL 让客户端直传对象存储，不经过应用服务器。

**Q：为什么限制 2MB？**

> 成员照片的展示尺寸也就几百像素，原图几 MB 完全没必要。**用约束代替优化**——限制输入永远比事后优化便宜。

**Q：怎么防路径穿越？**

> 保存时用 UUID 重命名，根本不用用户提供的文件名；删除时校验解析后的路径必须在上传目录内。两处都做了。

# 六、容器化部署：多服务编排与数据持久化

## ① 场景

服务器是实验室共享的，上面跑着别人的服务，没有随意折腾系统的自由。而应用要和数据库、缓存一起编排，还要保证长期稳定运行。

## ② 代码

三个服务，一个 compose 文件（`deploy/docker-compose.prod.yml`）：

```yaml
services:
  postgres:
    image: ${KB_DOCKER_REGISTRY}/pgvector/pgvector:pg17
    volumes: [kb-pgdata:/var/lib/postgresql/data]
    healthcheck:                       # 不是"启动了"就算就绪
      test: ["CMD-SHELL", "pg_isready -U kb -d kb"]
    restart: unless-stopped            # 服务器重启后自动拉起

  redis:
    image: ${KB_DOCKER_REGISTRY}/library/redis:7-alpine
    command: redis-server --appendonly yes --requirepass ${KB_REDIS_PASSWORD}
    volumes: [kb-redis:/data]
    restart: unless-stopped

  app:
    depends_on:
      postgres: { condition: service_healthy }   # 等真正就绪，而不是等容器启动
      redis:    { condition: service_healthy }
    volumes:
      - kb-uploads:/app/data/uploads             # 照片必须持久化
    restart: unless-stopped
```

镜像里不编译，只放产物（`deploy/Dockerfile`）：

```dockerfile
ARG BASE_IMAGE=docker.m.daocloud.io/library/eclipse-temurin:17-jre
FROM ${BASE_IMAGE}
WORKDIR /app
COPY target/ai-kb-agent-0.1.0-SNAPSHOT.jar /app/app.jar
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/app.jar"]
```

## ③ 原理

**三个卷，三种数据**：

| 卷 | 存什么 | 不挂的后果 |
|---|---|---|
| `kb-pgdata` | 数据库文件 | 重新部署数据全丢 |
| `kb-redis` | Redis AOF | 缓存和限流状态丢失（可接受） |
| `kb-uploads` | 上传的照片 | **重新部署照片全丢** |

**关键原则：容器的文件系统是临时的，任何需要留存的数据都必须挂卷。**

**健康检查为什么必要**：`depends_on` 默认只保证"容器启动了"，不保证"服务就绪了"。应用启动时要连数据库，数据库没就绪就会启动失败。用 `condition: service_healthy` 才能真正等待。

**`restart: unless-stopped` 为什么重要**：这是"长期维护"的基本保障。不能指望每次服务器重启或断电都有人手工启动服务。

## ④ 边界：一个真实的踩坑

**现象**：`docker pull` 卡住不动，最后超时。

**根因**：daemon 配置里的 `registry-mirrors` 没生效（配置后没重启过 Docker），Docker 回退去直连 Docker Hub，国内不通。

**解决**：**不改 daemon、不重启 Docker**，直接在 compose 里写**全限定镜像名** `docker.m.daocloud.io/xxx` 绕过。

**为什么这一点重要**：这台机器上跑着别人的容器。**在共享服务器上不能想当然地重启 Docker 或改系统配置**，能找到"不干扰他人"的解法是工程素养的体现。

## ⑤ 简历怎么写

> 使用 Docker Compose 编排应用、PostgreSQL(pgvector) 与 Redis 三服务，通过健康检查保证启动顺序、通过命名卷持久化数据库与上传文件、配置 restart 策略实现服务器重启后自动恢复。

## ⑥ 面试怎么答

**Q：为什么镜像里不编译，不用多阶段构建？**

> 多阶段构建适合 CI/CD 流水线。我们的约束是**服务器上没有 Node 和 Maven，且网络访问 Docker Hub 不稳定**，所以选"本地构建、只传产物"，代价是本地环境必须完整。如果上了 CI（比如 GitHub Actions），就该改成多阶段构建。

**Q：健康检查为什么重要？**

> 因为 `depends_on` 默认只保证容器启动了，不保证服务就绪。应用启动要连数据库，数据库没就绪就会启动失败。`condition: service_healthy` 才能真正等待就绪。

**Q：怎么更新线上版本？**

> 本地打包、上传 jar、服务器重新 build 并 `up -d`。Docker 会重建应用容器，数据卷不受影响。约两分钟，是停机更新；要做到零停机需要多实例加滚动更新，这个规模不需要。

**Q：容器日志怎么处理？**

> 默认输出到 stdout/stderr 由 Docker 收集，可以用 `docker logs -f` 查看。生产环境应该配日志驱动或挂载日志卷，避免日志写满容器磁盘。我们目前依赖 `docker logs`，够用但不够专业。

# 七、前后端分离的构建集成

## ① 场景

前端用 Vue，后端 Spring Boot。**怎么让它们一起部署，而服务器上不装 Node？**

## ② 代码

构建产物直接输出到后端静态目录（`frontend/vite.config.js`）：

```js
export default defineConfig({
  server: {
    // 开发时把 /api 代理到后端，避免跨域
    proxy: { '/api': { target: 'http://localhost:8080', changeOrigin: true } }
  },
  build: {
    // 前端产物直接落到 Spring Boot 的静态资源目录
    outDir: '../src/main/resources/static',
    emptyOutDir: true
  }
})
```

一键构建（`build.ps1`）：

```powershell
Push-Location frontend
npm install --no-audit --no-fund    # 装依赖
npm run build                       # 构建前端，产物输出到 src/main/resources/static
Pop-Location
mvn -DskipTests package             # 打包后端 jar
```

> 这里用切换目录而不是 `npm --prefix`：npm 10 的 `--prefix` 在 `install` 子命令上行为不一致，
> 会去当前目录找 `package.json` 而报 ENOENT。**跨版本的命令行工具，用最不容易产生歧义的写法。**

路由懒加载（`frontend/src/router/index.js`）：

```js
// 管理后台用动态 import：访客不会下载这部分代码，只有访问 /admin 才加载
{ path: '/admin', component: () => import('@/admin/AdminView.vue') }
```

## ③ 原理

**为什么把前端打进 jar**：部署变成"一个 jar、一个容器、一个端口"，不需要 Nginx 单独托管前端，也就不用处理跨域。**少一个组件、少一处配置、少一个故障点。**

**开发时怎么兼顾热更新**：Vite dev server 跑在 5173，通过 `proxy` 把 `/api` 转发到 8080。改前端即时生效，改后端重启后端。

**懒加载为什么重要**：管理后台被拆成独立 chunk（实测 10.5 KB），访客不下载它——**既减小首屏体积，也不把后台结构暴露给访客**。这是零成本优化，Vue Router 的动态 import 自动做到。

## ④ 边界

| 场景 | 方案 |
|---|---|
| 一个后端 + 一个前端，访问量不大 | **打进 jar（当前方案）** |
| 前端迭代频繁、需要 CDN | Nginx / 对象存储单独托管前端 |
| 前端要独立发布、灰度 | 前后端彻底分离，各自独立部署 |

## ⑤ 简历怎么写

> 采用 Vue3 + Vite + Spring Boot 前后端分离架构，通过 Vite 构建产物直出后端静态目录实现单 jar 部署；管理后台路由懒加载独立分包（10.5KB），访客首屏不加载后台代码。

## ⑥ 面试怎么答

**Q：为什么不用 Nginx 单独部署前端？**

> 两种方案各有场景。Nginx 单独部署适合前端迭代频繁、需要 CDN 的场景；我们这种"一个后端加一个前端、访问量不大"的情况，打进 jar 更简单——少一个组件、少一处配置、少一个故障点。如果以后前端要独立发布或做灰度，就该拆出去。

**Q：首屏体积多大算合理？**

> 一般目标是 gzip 后 200KB 以内。我们目前 349KB，偏大，原因是全局引入了 Element Plus 全部组件。优化方向是按需引入，或把组件库只放进管理后台的 chunk。**知道瓶颈在哪、知道怎么优化，比假装没问题好。**

**Q：为什么 gitignore 构建产物？**

> 构建产物是生成代码，提交进仓库会让 diff 没法看，也容易出现"改了源码忘了重新构建、仓库里是旧产物"。改成构建脚本保证顺序，仓库只存源码。

# 八、幂等导入：内容哈希与重复入库

## ① 场景

「同步知识库目录」这个按钮，用户会反复点——加了一篇文档点一次，改了一篇再点一次。

如果每次都是"全量重新入库"，同一份文件就会有 N 份副本。后果很直接：**同一段内容在检索结果里出现多次，挤占上下文、稀释注意力、还浪费 token**。

实测：点 3 次，知识库里每份文档就有 3 份副本。

## ② 代码

**入库前先算内容哈希，查一下有没有相同内容的文档**（`ingest/DocumentIngestionService.java`）：

```java
private Optional<DocumentRecord> findDuplicate(byte[] bytes, boolean skipIfExists) {
    if (!skipIfExists) {
        return Optional.empty();
    }
    return repository.findActiveByContentHash(sha256Hex(bytes));
}
```

**查询条件里排除了失败记录**：

```sql
SELECT * FROM kb_document
 WHERE content_hash = ? AND status <> 'FAILED'
 ORDER BY created_at DESC LIMIT 1
```

**批量导入因此可以反复执行**（`eval/EvalController.java`）：

```java
for (Path file : files) {
    SubmitResult result = ingestionService.submit(name, type, bytes, true);  // true = 跳过已存在
    if (result.skipped()) {
        skipped.add(name);       // 记录跳过了哪些
        continue;
    }
    submitted.add(name);
}
```

前端显示成一句话：**「已提交 2 个文件，跳过 4 个未改动的」**。

## ③ 原理

**为什么用内容哈希，不用文件名。** 文件名不可靠：

- 改了名字但内容一样 → 应该跳过，文件名判断会重复入库
- 内容改了但名字没变 → 应该重新入库，文件名判断会错误跳过

**为什么排除 FAILED。** 如果一个文件上次入库失败了（比如格式问题），用户修好格式后重新上传，**必须允许重试**。如果不排除失败记录，"一次失败就再也传不进来"。

**幂等性的价值**：一个操作执行一次和执行 N 次，结果相同。这让"同步"这个动作可以从"小心翼翼的定时任务"变成"随手点的按钮"——**用户不用记住上次同步到哪了**。

## ④ 边界：还没解决的两个问题

| 问题 | 现状 | 该怎么处理 |
|---|---|---|
| **内容微改**（改了个错别字） | 哈希变了 → 重新入库 → **旧版本还在** | 需要"同名文件替换"策略：入库前查同名文档，先删旧的再建新的 |
| **目录里删了文件** | 知识库里的不会自动删 | 需要"双向同步"：以目录为准，多余的知识库文档标记或删除 |

**这两个是"同步"和"只增不删"的区别。** 我们目前实现的是后者——安全（不会误删），但需要人工清理。

## ⑤ 简历怎么写

> 基于文件内容 SHA-256 实现幂等导入：同步操作可反复执行，未改动的文件自动跳过并反馈跳过数量；查询时排除失败记录以保证失败任务可重试，避免"一次失败永久阻塞"。

## ⑥ 面试怎么答

**Q：为什么用内容哈希而不是文件名？**

> 文件名不可靠。改名字但内容相同会重复入库；内容变了但名字没变会错误跳过。**用内容的哈希才能真实反映"这份资料是不是同一份"**。

**Q：如果一个文件上次入库失败了怎么办？**

> 查询时排除了 FAILED 状态。如果不排除，用户修好格式后重新上传会被当成"已存在"跳过，**等于一次失败就永久阻塞**。所以去重只针对"可用或处理中"的记录。

**Q：什么是幂等？为什么这里需要它？**

> 幂等是指同一个操作执行一次和执行多次，结果相同。这里需要它是因为——**用户不该需要记住"上次同步到哪了"**。有了幂等，同步按钮就可以随手点，不用小心翼翼。
> 分布式系统里幂等更重要：网络超时后重试是常态，没有幂等就会重复扣款、重复下单。

**Q：内容改了但文件名没变，会怎样？**

> 哈希不同，会被当成新文档入库，**旧版本还留在知识库里**。这是我们没解决的问题——正确做法应该是"同名文件替换"：先查到同名文档，删除它的向量和记录，再入库新的。
> 另一个方向的问题是：目录里删了文件，知识库里不会自动删。所以我们现在实现的是"只增不删"的同步，安全但需要人工清理。
